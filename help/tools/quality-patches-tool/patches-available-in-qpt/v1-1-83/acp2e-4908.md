# ACP2E-4908：大きなカタログが原因でRedisまたはValkey メモリが過剰に使用される

ACP2E-4908 パッチでは、各ストアビューで製品ごとに個別のレイアウトキャッシュエントリが作成されたため、大きなカタログが[!DNL Valkey] （または[!DNL Redis]）で過剰なメモリ使用を引き起こす可能性がある問題を修正します。 このパッチは、[[!DNL Quality Patches Tool (QPT)]](/help/tools/quality-patches-tool/quality-patches-tool-to-self-serve-quality-patches.md) 1.1.83がインストールされている場合に利用できます。 パッチ IDはACP2E-4908です。 この問題は、Adobe Commerce 2.4.10で修正される予定です。

## 影響を受ける製品とバージョン

**パッチはAdobe Commerceのバージョン**&#x200B;用に作成されました

* Adobe Commerce（すべてのデプロイメント方法） 2.4.8-p4

**Adobe Commerceのバージョンとの互換性：**

* Adobe Commerce（すべてのデプロイメント方法） >=2.4.8 &lt;2.4.10

>[!NOTE]
>
>このパッチは、新しい[!DNL Quality Patches Tool] リリースを含む他のバージョンに適用される可能性があります。 パッチがAdobe Commerceのバージョンと互換性があるかどうかを確認するには、`magento/quality-patches` パッケージを最新バージョンに更新し、[[!DNL Quality Patches Tool]：パッチの検索ページ ](https://experienceleague.adobe.com/tools/commerce-quality-patches/index.html)で互換性を確認します。 パッチ IDを検索キーワードとして使用して、パッチを検索します。

## イシュー

大きなカタログは、各ストアビューの製品ごとに個別のレイアウトキャッシュエントリが作成されるため、[!DNL Redis]または[!DNL Valkey]でメモリが過剰に使用される可能性があります。

<u>複製する手順</u>:

1. デフォルトのキャッシュバックエンドとして[!DNL Valkey] （または[!DNL Redis]）を設定します。
1. `app/etc/env.php`を編集し、cache.frontend.default ブロックを次のように設定します。

   ```
   'default' => [
       'id_prefix' => '061_',
       'backend_options' => [
           'server' => 'valkey',          // your Valkey/Redis hostname
           'port' => '6379',
           'database' => '1',
           'password' => '',
           'compress_data' => '0',        // key recipe — leaves XML uncompressed
           'persistent' => 0,
           'read_timeout' => 10,
           'connect_retries' => 2,
       ],
       'backend' => 'redis',
   ],
   ```

   次に`flush: bin/magento cache:flush`。

1. 中程度のパフォーマンスを発揮するフィクスチャを生成します。

   ```
   bin/magento setup:performance:generate-fixtures \
       setup/performance-toolkit/profiles/ce/medium.xml
   ```


   これにより、3つのweb サイト×3つのストアグループ×3つのストアビュー、24K シンプル+640設定可能な製品、33の属性セット、50Kの注文が生成されます。 高速マシンで10分。

1. [!DNL Valkey] `db1`をリセットしてウォームアップ：

   ```
   valkey-cli -h <host> -n 1 FLUSHDB
   bin/magento cache:flush
   ```

1. 店舗をまたいで商品ページをクロール。 サンプルリストを作成し、各URLを押します。

   ```
   # Build 200 random product URLs across stores 1–4
   mysql -e "SELECT CONCAT(s.code,'|',u.request_path)
             FROM url_rewrite u JOIN store s ON u.store_id=s.store_id
             WHERE u.entity_type='product'
               AND u.request_path NOT LIKE 'catalog/product/%'
               AND s.store_id BETWEEN 1 AND 4
             ORDER BY RAND() LIMIT 200;" magento > urls.txt
   
   while IFS='|' read -r STORE URL; do
       curl -s -o /dev/null "http://<base-url>/${URL}?___store=${STORE}"
   done < urls.txt
   ```

1. `LAYOUT` キャッシュフットプリントを監視します。

   ```
   valkey-cli -h <host> -n 1 --scan --pattern "*LAYOUT_FRONTEND_STORE*" | wc -l
   valkey-cli -h <host> INFO memory | grep used_memory_human
   ```


   お客様の10,000鍵 / 1.7 GBのレジームに到達するために、クロールをスケールアップします（または、`large.xml`/`extra_large.xml`と実際の読み込みツール （siege/workなど）を使用します）。

<u>期待される結果</u>:

圧縮が有効になっている場合、パフォーマンスは影響を受けません。

<u>実際の結果</u>:

- `LAYOUT_FRONTEND_STORE` [!DNL Redis] キーは、かなりの容量を消費します。
- 新規の中型インストールでは、200回の商品ヒットの後、約564個の`LAYOUT_FRONTEND_STORE` キーと約20 MBの`used_memory_human` （クロール前は約10 MB ベースライン）が表示されます。商品ページヒットごとに約2.8個のLAYOUT キャッシュキーが表示され、各店舗でユニーク商品がリニア×成長しました。
